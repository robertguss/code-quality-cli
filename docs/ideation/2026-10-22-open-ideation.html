Grounding Context

Codebase Context

qgate is a local, deterministic quality gate for code written by AI agents. It runs as git hooks, runs the repo's own linters and tests in parallel with built-in checks, and ends in one pass or fail. The built-in checks are function length (14 tree-sitter grammars), file length and cross-repo duplication. It also has a shrink-only baseline ratchet, a Claude Code PreToolUse hook that blocks hook skipping and tampering, loosening warnings, guard rule families and the qgate.features.toml feature map. It is built for agents: it never prompts, supports --format json, prints a fix: line on every failure and ships an agent skill.

  • Shape: about 16.6k lines of Rust. The largest module is agent_hook (3,567 lines of shell and git-argument parsing), followed by rules, features and guard. There are 422 tests and 6 end-to-end files.
  • Trajectory: v0.2 Elixir. v0.3 agent skill and persistent build checkout. v0.4 removed approvals, so loosenings now warn instead of block. v0.5 feature map. v0.6 rule families (escape-hatch, swallowed-error, debug-output) for Rust, TS/JS, Python, Go and Elixir, plus inline suppressions with reason and until.
  • Gaps with evidence:
    • Feature-map entry points are Rust-only (src/features/inventory/mod.rs:127).
    • Seven grammar languages have no rule families.
    • Heuristic rules get narrowed case by case after dogfooding (commit 0c42704).
    • The agent hook's fallback scans every argument of any command not known to be read-only (src/agent_hook/mod.rs:869-880). It produced a false positive during this run.
    • README "Known limits" concedes that hooks can be deleted and that only Claude Code is covered.
  • Already built (checked during critique):
    • qgate features init (src/features/draft.rs).
    • A persistent per-blob duplication token cache (src/checks/duplication/index.rs).
    • A pre-push gate against the merge base (src/hooks/run.rs:131).
    • Exact rules block, heuristic rules warn.
    • Expiry on suppressions.

External Context

  • --no-verify blockers are a commodity (block-no-verify, "No Excuses" hooks), so qgate's edge has to come from elsewhere.
  • Agents reward-hack tests. EvilGenie (MIT FutureTech, Nov 2025) measured Claude Code hacking 2.1% of unambiguous problems and 33.3% of ambiguous ones, and treats test-file edits as likely hacks. No gate that protects tests turned up.
  • Agents duplicate code. GitClear 2025 found that duplicated blocks of five lines or more rose 8x in 2024 and moved lines fell 39.9%. GitClear attributes this to AI not reusing existing functions because it has limited context.
  • Hook-based guardrails in the market target Claude Code only. Other agents run git directly.

Topic Axes

Decomposition skipped — surprise-me mode. Each frame chose its own subject, and the survivors cluster on four: test integrity, agent-hook trust, language coverage, and feedback that arrives earlier in the agent's loop.

1. Test-integrity ratchet

Description
Add a tests rule family that uses the baseline in the opposite direction. Today the baseline holds counts of bad things, which may only shrink. This family records counts of good things per test file and function: test count and assertion count, which may only grow. New skip, xfail, .only or #[ignore] markers and deleted tests count as regressions. A deliberate weakening goes through the normal loosening path with a reason. The sharpest version borrows from clinical-trial pre-registration: flag a test weakened in the same change as the source code it covers. That is the "change the grader after seeing the result" pattern. Build it as the first "must not fall" counter, so the counter direction is the only new concept in the baseline.
Basis
external: EvilGenie (MIT FutureTech, Nov 2025) found Claude Code reward-hacks 33.3% of ambiguous problems and flags edits to test files as likely hacks. No existing gate that protects tests turned up. direct: the baseline format rule<TAB>path<TAB>symbol<TAB>count has no length-specific fields. Nothing in the guard protects tests today: src/guard/ignores.rs covers @ts-ignore-style markers, not .only, xfail or #[ignore].
Rationale
Telling an agent to make the tests pass gives it a cheap shortcut: weaken the tests. Every other qgate check trusts the test suite, so protecting it raises the value of the whole gate. All six ideation frames proposed this independently. It also reuses the ratchet, the suppressions, the loosening warnings and the per-language RULES tables, and it sets qgate apart from the commodity bypass blockers.
Downsides
Assertion counting is heuristic in each language, and legitimate refactors (merging two tests, swapping a matcher) will cause churn. They need a clean exemption path. The "same change as the covered source" heuristic needs a mapping from tests to source, which will be approximate.

2. Explainable, position-aware agent hook

Description
Replace the hook's generic fallback with a per-command table of argument positions that can write a path. Today the fallback treats every argument of a command not known to be read-only as a possible write target. Under the new table, inline interpreter code (python -c, node -e) is opaque except for literal protected paths. Every denial names the matched token, the protected path it resolved to and a fix line that applies to the case. Add qgate hook explain '<cmd>' to replay a decision. Back the hook with a labelled corpus of harmless and hostile commands as regression tests, so a narrowing cannot quietly open a bypass. Each new false positive becomes a corpus entry.
Basis
direct: src/agent_hook/mod.rs:869-880: "The generic fail-safe: any argument naming a protected path or carrying a marker blocks a command not known to be read-only". mentions_bypass at :181-183 is a substring match. direct: during this ideation run, the hook denied a harmless python3 -I -c "<script>" … /tmp/… that only wrote a JSON file under /tmp. The message quoted the whole script as "protected (git hooks, git config or Claude Code hook settings)" and gave the fix line "Fix the reported findings and commit normally."
Rationale
The hook is qgate's trust surface and its largest module. A denial that names no path and gives a fix line that doesn't apply breaks the "every failure prints the command that resolves it" promise. It also teaches agents and humans to route around the hook, which is the behavior qgate exists to stop. The corpus makes every future tightening or loosening of the hook testable.
Downsides
Each narrowing is a potential bypass, so the corpus has to come first. Maintaining a table of write positions for common commands is ongoing work. Opaque interpreter code is still an unchecked channel, as it already is per the README's known limits.

3. Rules and entry points as tested query packs

Description
Move rule families and feature-map entry-point discovery out of per-language Rust into declarative tree-sitter query packs, one per language over the 14 bundled grammars. Entry points are routes, CLI commands, binaries and migrations. Each pack has a metadata header with scope keys such as outside-tests and main-guard, plus golden fixtures showing where each rule must fire and must not fire. Narrowing a rule that over-fires becomes a data change with a fixture, not a Rust patch after a release. The first goal is entry-point packs for TypeScript, Python and Go, so the feature map reaches the repos agents write most.
Basis
direct: src/features/inventory/mod.rs:127 reads .filter(|p| Lang::detect(p) == Some(Lang::Rust) && in_scope(p)). src/rules/lang/mod.rs covers only rust, python, go, typescript and elixir. Rule queries are already tree-sitter strings compiled once (src/rules/lang/mod.rs:93-112). Commit 0c42704, "Narrow Python and Elixir rules after dogfooding on public repos", added under_main_guard and Scope::OutsideTests as a one-off fix. external: Semgrep and CodeQL treat rules as declarative data.
Rationale
The v0.5.0 notes describe routes, commands and binaries generically, so a TypeScript or Python adopter will assume the feature map works for them. Today it silently does nothing, which leaves a gap between the docs and the code in qgate's main defense against scope creep. Shipping fixtures with the packs turns each dogfooding lesson into a regression test, so adding Java or tightening Python stays cheap and safe.
Downsides
Some rule logic, such as context checks like the main guard, may not fit pure queries and would need an escape hatch back to Rust. Entry-point detection for web frameworks is framework-specific (Express, Next, FastAPI and Flask each differ), so coverage will be uneven. This is a sizeable refactor of working code.

4. qgate selftest: prove the gate is armed

Description
Add a command, modeled on a smoke detector's test button, that proves the gate works end to end. It checks four things:
  • The hooks resolve through the effective core.hooksPath.
  • The hook files are present, executable and match what qgate install wrote.
  • The binary matches the qgate_version pin.
  • A seeded violation in a scratch worktree exits 1.
It prints a fix: line for each failed check. The agent skill runs it at session start, qgate update runs it afterwards, and pre-push can run a cheap subset.
Basis
direct: README "Known limits" (README.md:448-455) says "Anyone with a shell can delete the hooks", "The agent hook covers Claude Code only" and "Clones without qgate install are not gated". The critique pass found no run-time check of core.hooksPath or the hook files, and no doctor or selftest command. external: other agents (Codex, Cursor, Aider) run git directly, so the git hooks are the only gate they meet.
Rationale
A disarmed gate fails silently, which is worse than an absent one, because everyone assumes it is running. This turns "the gate is installed" into something any agent can check, including agents that aren't Claude Code. It is the cheap, honest core of a larger "witnessed commits" idea, which was cut (see the Rejection Summary).
Downsides
It detects disarming only when something calls it. A determined actor can skip the selftest too, which matches the README's stated boundary. The seeded-failure step costs a worktree and a gate run, so the per-push version must stay small.

5. Edit-time feedback through a PostToolUse hook

Description
Install a Claude Code PostToolUse hook for Edit and Write next to the existing PreToolUse guard. It runs only the single-file, millisecond-scale checks on the file just changed: function length, rule families, suppression syntax and whether the path falls inside a declared feature. It returns any fix: lines to the agent in the same turn. The full gate still runs at commit and push.
Basis
direct: src/hooks/install.rs:252 registers only hooks.PreToolUse, and the critique pass found no --changed mode. reasoned: function length and the rule families are per-file, deterministic and fast, so their results are known the moment the file is written. Reporting them at commit time means the agent may already have built on the bad shape across many edits, and fixing it then costs a rewrite rather than one edit.
Rationale
Agent token cost goes into rework. Feedback inside the turn changes "write, commit, fail, rewrite" into "write, fix". It also makes qgate part of how the agent writes code rather than a checkpoint at the end.
Downsides
It works only in Claude Code, like the existing hook. It risks feedback noise in the middle of a refactor, when intermediate states are legitimately over the limit, so it may need to warn rather than block. It adds latency to every write.

6. qgate similar: reuse before you write

Description
Turn the duplication machinery from a judge into a source of context. qgate similar --format json <file|stdin> returns the existing functions closest to a snippet, with path:line. The agent skill tells agents to run it before adding any helper longer than a few lines. Later, the edit-time hook (idea 5) could reply "this new function closely matches foo::bar at path:line" in the same turn.
Basis
external: GitClear 2025 (211M changed lines) found that duplicated blocks of five lines or more rose 8x in 2024 and moved lines fell 39.9%. GitClear attributes this to AI being less likely to reuse existing functions because it has limited context. direct: qgate already tokenizes every blob and caches the tokens persistently (src/checks/duplication/index.rs: "Per-blob token cache under .git/qgate/").
Rationale
The duplication check rejects copies after they are written, but the research says the cause is that the agent couldn't see the existing function. Retrieval addresses the cause, and no pass/fail linter offers it.
Downsides
The cache holds tokens per blob, not an index of similarity per function, so this needs a new function-level index. Token-clone matching finds near-verbatim copies, not functions that are similar in meaning. Agents will use it only if the skill makes it habitual.
