## Upgrading from v0.4.1

Run `qgate update`, bump the pinned version, rewrite the agent skill, and
record the new rules' existing hits in the baseline:

```sh
qgate update                      # installs v0.5.0 over the running binary
$EDITOR qgate.toml                # qgate_version = "0.5.0"
qgate install                     # writes the skill for v0.5.0
qgate baseline create --force     # adds counts for the new rules
git add qgate.toml qgate.baseline .claude/skills/qgate .agents/skills/qgate
git commit -m "Upgrade qgate to v0.5.0"
```

The new baseline entries are reported as one `upgrade to 0.5.0` warning, not
as loosenings, as long as they match what the tree already had. Length and
duplication entries are measured as before.

## Rules

- Every check has a rule id, kind (exact or heuristic), level, source and
  rationale. `qgate rules` lists them; `qgate rules <id>` explains one.
- `[rules]` in `qgate.toml` sets `error`, `warn` or `off` per rule or family.
  Lowering a level is a loosening.
- New rule families, counted per file and ratcheted like lengths, for Rust,
  TypeScript and JavaScript, Python, Go and Elixir: `escape-hatch`,
  `swallowed-error` and `debug-output`. Exact rules fail; heuristic ones warn.
- `[rules.debug-output] allow = [...]` lists paths where printing is the file's
  job. Binary entry points and scripts are exempt already.
- `// qgate: allow <rule> -- reason: ..., until: YYYY-MM-DD` takes one
  occurrence out of a count.

## Suppressions

- A new suppression comment needs `reason:` and `until:` on its line, at most
  90 days ahead (`[suppressions] max_days`). Expired ones fail when their file
  changes. Moving a date later is a loosening.
- Suppressing anything on `[suppressions] always_block` fails: by default the
  exact `swallowed-error` rules, `@ts-ignore`, `@ts-nocheck` and a bare
  `eslint-disable`. So does a config or baseline edit that lowers, removes,
  excludes or grows those rules. This is the one place a loosening blocks.
