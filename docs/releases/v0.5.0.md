## Upgrading from v0.4.1

Run `qgate update`, bump the pinned version, and let `qgate install` write the
new agent skill and draft a feature map:

```sh
qgate update                      # installs v0.5.0 over the running binary
$EDITOR qgate.toml                # qgate_version = "0.5.0"
qgate install                     # writes the skill and drafts qgate.features.toml
$EDITOR qgate.features.toml       # name the placeholders you know (optional)
git add qgate.toml qgate.features.toml .claude/skills/qgate .agents/skills/qgate
git commit -m "Upgrade qgate to v0.5.0"
```

The first commit of the map is an adoption: nothing in it counts as a new
feature, and placeholders need no purpose or task. Code is measured the same
way as v0.4.1, so baselines don't need to be recreated.

After upgrading, a new top-level module, binary, route, CLI command or
migration must belong to a feature in `qgate.features.toml`, or the run fails
with `feature-unowned`.

## The feature map

`qgate.features.toml` lists what the repo is for: each feature's purpose, the
task that created it, and the folders and files it owns. qgate finds the entry
points in production code (binaries, axum routes, clap subcommands,
migrations and top-level modules) and checks each one belongs to a feature.

- `feature-unowned` (error): an entry point outside every feature.
- `feature-stale` (error): a folder or listed file that no longer exists.
- `feature-map`: the map doesn't parse, repeats a feature, gives a named
  feature no purpose, or gives one folder to two features (errors); a feature
  that owns a whole source root is a warning.
- `feature-task`: a new feature, or a placeholder given a name, needs a `task`
  matching `[tasks] pattern`, and on push that ID must be in the branch name or
  a pushed commit message. At commit a missing match is only
  `feature-task-pending` (info).
- `scope-change` (info): one line per map edit. On push, the report's `scope`
  line (`data.scope` in JSON) sums up the change for a pull request
  description, such as
  `new feature search (QG-31): 1 binary, 1 module, 1 folder, +1,240 lines`.
- Deleting the map, or changing `[tasks] pattern`, is a `loosening`.

## New commands

- `qgate features init [--force] [--dry-run]` drafts a map of placeholder
  features from the code: one per top-level module, plus one per folder of the
  remaining entry points. `qgate install` runs it when there is no map.
- `qgate features show [NAME]` prints where each feature lives and which entry
  points no feature owns.
- `qgate features log [--since REV]` lists the scope changes of every commit
  that changed the map.

The agent skill explains the new findings and commands.
