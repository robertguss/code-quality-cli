## Upgrading from v0.2.0

Bump the pinned version in each repo and approve it:

```sh
$EDITOR qgate.toml                # qgate_version = "0.3.0"
qgate install                     # writes the new agent skill
git add qgate.toml .claude/skills/qgate .agents/skills/qgate
qgate approve                     # the version bump needs approval
```

v0.3.0 measures code the same way as v0.2.0, so baselines don't need to be
recreated.

## Agent skill

- qgate now carries an agent skill that explains the gate to an agent that has
  never seen it: how to read and fix findings without loosening the gate, what
  needs approval, how the baseline ratchet works, and how to set qgate up.
  `qgate --skill` prints it, matched to the installed version.
- `qgate install` writes the skill to `.claude/skills/qgate/SKILL.md` (Claude
  Code) and `.agents/skills/qgate/SKILL.md` (Codex and other agents). Commit
  both.
- Every run checks the committed copies. A copy from an older release is a
  `skill-outdated` warning that says to run `qgate install`. A copy edited by
  hand is a `skill-edited` error, so an agent can't rewrite the instructions
  later agents read; `qgate install` restores it. A missing copy is a
  `skill-missing` warning.

## Build isolation

- Repo tools that can't run in the working tree (always at push, and at commit
  when the tree differs from what is staged) now run in one persistent
  checkout at `.git/qgate/checkout`, updated in place. Builds there stay
  incremental, and build output such as `_build`, `target` and `.gradle` stays
  in the checkout, so a tool run never writes into your own build or waits on
  its lock. Installed dependencies are still linked in from your working tree.
- The first run after upgrading is slow while the checkout builds. Delete
  `.git/qgate/checkout` to reclaim the space; the next run rebuilds it.
